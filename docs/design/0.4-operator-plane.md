# Chat Admin 0.4 — operator plane design

- Status: **proposal for discussion.** Nothing here is implemented or accepted. The existing ADRs 0001–0006 stay as written until the revisions in §6 are agreed.
- Baseline reviewed: Chat Admin **0.3.3.1** (`main` = `9948d11`).
- Versioning: this is the **Chat Admin** 0.4 line. PrivaNet **Core** is a separate line (`0.4.0-alpha.4` at review time, `PrivaNet-Core` `dd13928`). Every "Core" statement below refers to that checkout, not to Chat Admin 0.4.
- Method: every claim marked **[V]** was verified against the repository (code read, test run, or a scratch experiment described in Appendix A). **[R]** marks a recommendation or judgement. Nothing was run against a deployed system; the experiments used temp paths on this container.

---

## 0. Summary

1. The 0.3.x split (unprivileged MCP frontend, separate unprivileged shell account, minimal root broker, exact-command TOTP root path) is sound and worth keeping. The sudo path in particular is well built.
2. **The approval layer for everything except `system.sudo` is not a security boundary today.** The grant/deny helpers are hidden from the model only by `visibility:["app"]` metadata, which the server lists and serves like any other tool, and the MCP port has no authentication. A plain local HTTP client completed request → grant → privileged action against the real broker and server code with no human (Appendix A). The command sandbox user can reach loopback, so the README claim that `run_command` "cannot directly mint approvals" does not hold for the scoped leases. This is the first thing 0.4 has to fix, and it shapes the rest of the design.
3. The tool surface (38 model-visible + 6 app-only tools, 0 MCP annotations) is organised around the *authorization mechanism* (`request_*`, `*_request_id`, `AUTHORIZATION_REQUIRED` retry dance) rather than around operator tasks. 0.4 should move to *proposal-on-first-call* with parameter-bound approvals.
4. Recommended architecture: a versioned **Operator API** inside the unprivileged Admin service, with MCP, a web panel, and a CLI as thin clients; a **principal model** in which an MCP transport/session is never an identity and an assistant principal can never be an approver; and **broker v2** that verifies approver proof bound to the exact operation instead of trusting the bridge's say-so.
5. Remote-node administration cannot be built on Admin alone. Core's admin API today has no node-management operations, no scoped admin credentials, and no admin capability discovery. ADR 0003/0006 are "Accepted" but depend on Core work that does not exist yet.
6. The automatic `privanet.updates` policy is compatible with your rules, but "verified" currently means "SHA-256 from the same GitHub Pages origin". For the Chat Admin self-update that is a root-code-execution path (`deploy.sh` plus an unpinned `pip install`) reachable zero-prompt by the model. Recommendation: define "verified" as *signed, monotonic, same-series*, and apply the automatic policy only to updates that meet it.

## 1. Architecture assessment of 0.3.3.1

### 1.1 What is solid and should be kept

| Property | Evidence |
| --- | --- |
| Three identities: `privanet-chat` (MCP frontend), `privanet-shell` (sandbox), root broker; broker DB and TOTP secret in a root-only dir | `deploy.sh` (`BROKER_STATE_DIR` `0700 root`; broker `Group=$BROKER_GROUP`; shell not in broker group) **[V]** |

| Test suite passes: 60 tests (Python 3.13 here; CI matrix 3.11/3.13) | `pytest -q` **[V]** |

### 1.2 Structural findings

**F1 — Approval is not authenticated as human (critical). [V]**
- `grant_admin_access`, `grant_action_confirmation`, `deny_*` are registered with `visibility=["app"]` (`server.py:278–413`; the sudo helpers included). `tools/list` returns all 44 tools including these six, each carrying the visibility only as `_meta.ui.visibility`. The server never checks who is calling.
- The MCP endpoint is `uvicorn agent.server:app --host 127.0.0.1 --port 8787` with no authentication (`deploy.sh` unit); trust comes only from the tunnel in front of it.
- `privanet-chat-shell.service` allows `AF_INET AF_INET6` and has no `IPAddressDeny` (`deploy.sh:185`), and the README itself lists `curl http://127.0.0.1:4020/health` as a normal `run_command` use. So an unprivileged sandbox process can speak MCP to `127.0.0.1:8787`.
- Experiment (Appendix A): real `agent.broker` + real `agent.server` on temp paths; a stdlib HTTP client with no access to the broker socket called `request_admin_access` → `grant_admin_access` → `restart_service` and got `authorization: approved`; the broker then ran `systemctl restart` (which failed only because this container has no systemd). The same client walked `system.packages` → `install_system_package` → `request_action_confirmation` → `grant_action_confirmation` → `install_system_package`; the broker accepted the capability and confirmation and proceeded to the root `apt-get` step.
- Not bypassed: `system.sudo` (TOTP verified inside the broker; the seed is root-only) and nothing in the broker accepts a lease for it.
- Whether ChatGPT hides app-only tools from the model is host behaviour I cannot verify from this repo. That is exactly why it cannot be the boundary: ADR 0002 already says "approval is not inferred from a model/tool request alone", and the roadmap says "no treating an MCP UI button as the sole security boundary without broker-side validation". The broker-side validation for scoped leases currently validates a lease's existence, not that a human created it.
- Consequence: for `privanet.services`, `privanet.nodes` (including `approve_node` with arbitrary capabilities and `revoke_node`), `privanet.node_local`, and `system.packages` (root `apt-get` with maintainer scripts), the human gate is advisory.

**F2 — Scoped leases are ambient authority, not operation approvals. [V]**
- A lease binds `(request_id, scope, expiry, uses)`. A 60-minute `privanet.nodes` lease covers `approve_node` with *any* capability list, `rename_node` for any node, `revoke_node` (which additionally needs a target-bound confirmation).
- `request_admin_access.reason` is model-authored free text; the lease is not bound to it. The card shows scope, `allows` text and the model's reason; it does not show the operation that will run.
- `get_authorization_status` returns every active lease with its `requestId`, so any later context can enumerate and use live handles for the rest of the lease lifetime **[V]** (`broker.py` `auth.status`).
- Only two operations (`admin.node.revoke`, `package.install`) have target binding, via the second confirmation.

**F3 — The broker is serial and the bridge times out at 10 s. [V by inspection; not exercised against systemd]**
- `broker.main()` handles one connection at a time (`broker.py:946`). `update.check`, `update.apply` (up to 7200 s), and `package.install` (up to 1800 s) run synchronously in that loop.
- `BrokerClient` uses `broker.timeout_seconds` = 10 for every action (`core.py:235`, `config.example.json`). So a real update through `apply_available_updates` raises `socket.timeout` in the bridge after 10 s while the broker keeps working, blocking every other broker call (including approvals and TOTP grants) until it finishes. The bridge audit row is never written because the exception propagates first.
- Tests use `FakeBroker` and cannot see this.
- `get_privanet_summary` calls `check_updates()` on every invocation. Experiment: a single broker timeout on `update.check` makes the whole summary raise `TimeoutError` instead of returning partial results **[V]**.

**F4 — The privileged audit trail is thinner than the bridge's, and the bridge's is writable by the bridge. [V]**
- Broker audit (`/var/lib/privanet-chat-admin-broker/`, root-only) records `admin.node.approve` with only the request code, not the capabilities granted (`broker.py:823`). The capabilities appear only in the bridge audit, which lives in a directory owned by `privanet-chat` (`deploy.sh`), i.e. writable by the component it audits.
- `audit_recent` swallows any broker error and returns bridge rows alone (`core.py:768`), so a broker audit failure looks like an empty history.
- The `session` column is labelled and merged like an identity but is a random per-session token; the only fallback identity is `local_<random>`. There is no principal or approver recorded anywhere.

**F5 — Verified-update path is stronger for Core apps than for Chat Admin itself. [V]**
- Core's `privanet-update` (Core repo `deploy/bin/privanet-update`, `docs/AUTOMATIC_UPDATES.md`): same major/minor series only, never downgrades, numeric pre-release ordering, lock file, bounded archive extraction, no downloaded scripts executed, state backup, symlink swap, rollback on start failure. Core's own doc says the SHA-256 "proves agreement with the same trusted repository's release manifest, not independent signing".
- Chat Admin's `update.sh`: compares `CURRENT == LATEST` only (`update.sh:83,92`), so a manifest that names an *older* release is installed; no lock; verifies SHA-256 taken from a manifest served by the same origin (`doopydoop364.github.io`) as the zip; then runs the unpacked `deploy.sh` **as root**, which runs `pip install --upgrade pip` and `pip install 'mcp>=2,<3' 'pydantic…' 'uvicorn…'` with no hashes or lock (`deploy.sh:51–52`).
- `update_chat_admin` and `apply_available_updates` take no approval and no parameters. `apply_available_updates` therefore installs whatever is current at call time, not what the model previewed with `get_update_status`.
- Therefore compromise of the Pages repo or of PyPI resolution on the host yields root on every host whose assistant calls `update_chat_admin` — without a human, and (via F1) without even the assistant's cooperation.

**F6 — Diagnostics are validated against fabricated fixtures, not Core's schema. [V]**
- `diagnose_node` reads `node["pressure"]` / `node["resourcePressure"]` (`core.py:534`). Core's `NodeView` nests it as `resources.pressure` (`packages/protocol/src/index.ts`, `NodeViewSchema`/`ResourceReportSchema`). Experiment with a Core-shaped node (`status: ONLINE, resources:{pressure:"HIGH"}`) returns only `HEALTHY`. The unit test passes because its fixture invents a top-level `pressure`.
- Core's statuses are `ONLINE, STALE, OFFLINE, DRAINING, OFFLINE_EXPECTED, REVOKED`. `diagnose_node` maps `STALE` and `DRAINING` to code `OFFLINE`; `privanet_summary` counts only literal `OFFLINE`.
- `version_drift` groups by `daemonVersion` string. Core's operator-dashboard doc states version is "a note, not a verdict: the protocol decides compatibility". Drift ignores `protocolVersion`, capability set, and `resources` shape.

**F7 — Core does not offer what ADR 0003/0006 assume. [V]**
- Coordinator admin routes (`apps/coordinator/src/server.ts`): `applications`, `enrollment-tokens`, `invites`, `nodes` (list/show/revoke/rename), `requests`, `storage`, `storage/keys/rotate`. There is no drain, maintenance, slot, restart, update, or diagnostics operation; `DRAINING` is node-initiated via heartbeat `lifecycle`. Node slots are set locally (`privanet-node slots`, `PRIVANODE_JOB_SLOTS`), which is why 0.3 has *local-only* slot tools.
- One all-powerful `PRIVANET_ADMIN_SECRET`; no scoped or read-only admin credential; "no administrator account/SSO system" (`docs/security.md`).
- The broker (root) reaches Core only by running the Node CLI wrapper `privanet-admin`, which sources `/etc/privanet/coordinator.env`. Consequently even pure reads (`nodes list/show`, `requests list`) go through the root broker, so a read-only node listing runs with the admin secret as root. That is the opposite of a minimal broker.
- `GET /v1/capabilities` is application-scoped and lists job types with online nodes. There is no admin capability/version discovery endpoint. Node heartbeats do carry `daemonVersion`, `protocolVersion`, `capabilities`, optional `services` and `resources` (all additive within protocol 1).
- Core already ships an operator dashboard (`privanet-admin ui`, loopback, session-token, CSRF, nonce CSP) covering nodes, join requests, invites. The Admin panel must define its relationship to it (§5, ADR 0010).

**F8 — Roadmap/repo hygiene. [V]**
- `ROADMAP.md` says published baseline is 0.3.2; the published manifest is 0.3.3.1 (`doopydoop364.github.io/privanet-chat-admin-latest.json`, whose `version` field is the non-numeric alias `0.3.3-hotfix.1` with `releaseVersion` `0.3.3.1`).
- Eight `.pyc` files are tracked and there is no `.gitignore`.
- The version string is hand-maintained in `pyproject.toml`, `core.py`, `deploy.sh`, `plugin.json`, the broker User-Agent, and a test that asserts the literal `0.3.3.1`.
- CI runs on push to `main` and `v0.3.*` only and does compile + pytest; there is no shellcheck, no lint, no tools-list contract test. UI, MCP-surface and docs assertions in the test suite are source-string greps (e.g. `'visibility=["app"]' in text`), which would pass while F1 is exploitable.

## 2. UX problems and awkward boundaries

### 2.1 Approval and confirmation UX

| # | Problem | Evidence |
| --- | --- | --- |
| U1 | **Three request tools + six grant/deny helpers + `AUTHORIZATION_REQUIRED` retry dance.** The model must thread `authorization_request_id` *and* `confirmation_request_id` through retries; a privileged call costs 3–5 model round trips and can fail at any hop. | `server.py` tools; SKILL rules 16–18 |
| U2 | **The card cannot show the operation.** It shows scope + model prose. For a lease the human is approving a *class* of action for 15–60 min, which is hard to reason about on a phone. | F2 |
| U3 | **No way to read back approval state.** `get_authorization_status` lists live leases only; pending, denied, expired and consumed are indistinguishable from "never existed". The model learns of approval only via the widget's `sendFollowUpMessage`, which is host-dependent. | `broker.py` `auth.status` |
| U4 | **Duration radio for every scope**, including destructive ones, and "this action only" lease can be spent by a different action in the same scope. | `auth.grant` |
| U5 | **Two-card flow for destructive actions** (scope card, then confirmation card) with a separate 5-minute clock each. | `confirm.*` |
| U6 | **TOTP typed into a host-rendered iframe** on the phone; the code transits the host. It is single-use and replay-protected, but it is the only approver factor and it is typed where the assistant's host can observe it. | `server.py` sudo path |
| U7 | **Fallback is a root shell on the server** (`privanet-chat-admin-authorize`) — unusable from a phone. `--create-scope privanet.updates` is offered but the broker rejects it. | `authorize.py:13` vs `broker.py` `APPROVAL_SCOPES` |
| U8 | **Request expiry is 5 min but the lease clock is separate**; the card has a countdown for the request only. | `auth.prepare`/`auth.grant` |

### 2.2 Tool-surface problems

| # | Problem |
| --- | --- |
| T1 | **Naming mixes mechanism and domain.** `request_admin_access`, `revoke_admin_access`, `get_authorization_status` (access vs authorization), `request_sudo_command` / `run_sudo_command` / `run_command`. |
| T2 | **Read-named tools with side effects.** `get_update_status` runs a fresh network check through the root broker; `get_privanet_summary` does too. |
| T3 | **Overlapping reads.** `get_privasearch_health` / `_status` / `_summary`; `get_services` / `get_service_status` / `get_system_health`; `get_nodes` / `get_node` / `get_pending_nodes` / `diagnose_node` / `get_node_version_drift` / `get_local_node_slots`. |
| T4 | **Update tools split by target kind** (`apply_available_updates`, `update_chat_admin`, `get_chat_admin_update_status`, `get_update_status`, `get_update_history`, `get_update_schedule`) with different semantics, none plan-bound. |
| T5 | **Local vs remote node asymmetry.** `set_local_node_slots` exists, remote slots cannot, and the skill text has to explain the difference. A single `set_node_slots(node)` with capability reporting would hide transport. |
| T6 | **No annotations at all** (0 of 44 have `readOnlyHint`/`destructiveHint`/`idempotentHint`/`openWorldHint`), so the host cannot apply its own safe defaults; read/write distinction lives only in prose. **[V]** |
| T7 | **All-or-nothing aggregates.** `get_privanet_summary` fails entirely when any section fails (F3); no per-section status or freshness. |
| T8 | **Unbounded free-form escape hatch next to typed tools.** `run_command` is correctly unprivileged, but with no operation record it is invisible in the same history as typed actions. |
| T9 | **Static, unversioned tool list.** There is no handshake that lets a client learn which operations a target supports (needed for ADR 0006); clients cache tool schemas. |

### 2.3 Update/self-update UX

- No preview-then-apply binding (F5). The model is told to "explain what the update check found", but the apply call cannot be tied to that explanation.
- `update_chat_admin` returns `STARTED` and the MCP bridge then restarts underneath the conversation. Nothing durable says "an update to X is in flight; verify bridge+broker version == X; roll back otherwise". The skill tells the model to verify "the live bridge version"; the only source is `get_command_environment.bridgeVersion`/`get_system_health.bridgeVersion`.
- There is no rollback tool, no release-note surface, no compatibility pre-check, no policy knob (every update class is zero-prompt or nothing).

### 2.4 Audit/history/runbook UX

- Two SQLite audit stores with different columns, merged by timestamp only; no correlation id from request → approval → grant → execution → verification (the roadmap's "audit timeline" cannot be built on this).
- Failures are summarised to `stderr or stdout[-1000:]` strings; no structured result, no `params_digest`.
- Broker keeps no operation result. After a bridge timeout (F3) or restart the outcome of a mutation is unknowable, which is the precondition ADR 0005 says must be reconcilable.

### 2.5 Mobile

The card is already thumb-friendly (stacked buttons, 1-column choices, numeric one-time-code input, fullscreen retry). Remaining mobile problems are architectural, not CSS: the human must go through the model to approve (U1), type TOTP into a host iframe (U6), cannot see history or state outside the chat, and the only fallback is SSH-grade (U7).

## 3. Proposed 0.4 client / API / UI architecture

### 3.1 Layers

```text
 Clients (thin, interchangeable)
 ┌──────────────┐  ┌────────────────────┐  ┌──────────────────┐
 │ MCP adapter  │  │ Web panel (PWA)    │  │ CLI              │
 │ assistant    │  │ operator principal │  │ local-root       │
 │ principal    │  │ passkey/TOTP login │  │ SO_PEERCRED      │
 └──────┬───────┘  └─────────┬──────────┘  └────────┬─────────┘
        │ in-process          │ HTTP 127.0.0.1:8788   │ unix socket
        ▼                     ▼                       ▼
 ┌───────────────────────────────────────────────────────────────┐
 │ privanet-chat-admin.service  (user privanet-chat, unprivileged)│
 │  Operator API  /v1  (service layer; one code path for all clients)
 │   principals · operations/proposals · approvals · runbooks     │
 │   read model + adapters: Core, services, Search, Proxy, Drive  │
 │   Admin SQLite (policy, history, runbook state, config history)│
 └───────┬──────────────────────────────┬────────────────────────┘
         │ broker v2 (unix socket)      │ scoped read credential /
         │ typed ops + approver proof   │ typed management ops (Core ADR)
         ▼                              ▼
 ┌─────────────────────┐        ┌──────────────────────────────┐
 │ root broker (minimal)│        │ PrivaNet Core Coordinator    │
 │ typed ops, op ledger │        │ authoritative network state; │
 │ privileged audit chain│       │ node management ops (future) │
 └─────────────────────┘        └───────────┬──────────────────┘
                                             │ existing outbound node relationship
                                             ▼
                                        PrivaNodes (owner policy decides)
```

Rules **[R]**:
- **One service layer, many transports.** MCP tool handlers call the same in-process functions the HTTP API calls. No MCP-only business logic. `core.py` (771 lines, one `AdminBackend`) is split by domain (nodes, services, updates, search, approvals, audit) behind that layer.
- **Operator API** is versioned (`/v1`, `X-Admin-Api-Version`), additive-only within a version, OpenAPI-described, and bound to loopback HTTP + a unix socket. It does not replace the existing `:8787/mcp` endpoint, so the OpenAI Secure MCP Tunnel configuration is unchanged.
- **The Operator API is not Core's API.** It does not proxy Core's admin API wholesale. Admin owns policy, approvals, history and orchestration (ADR 0001). Core remains the source of live network facts; Admin keeps no competing node/job table (ADR 0004).
- **Reads do not need root.** Core should issue a read-only admin credential (Core ADR, §6.2) readable by `privanet-chat` via group; the Operator API reads Core directly. The broker keeps only mutating operations, systemd status/logs, and secrets-bearing local reads (PrivaSearch token). This removes the "admin secret as root for every list call" pattern (F7).
- **No arbitrary remote shell, anywhere in this diagram.** The only free-form execution remains `run_command` (unprivileged, local) and `run_root_command` (exact command, TOTP, local).

### 3.2 Principals and approver authority

**[R]** Replace session-based audit with an explicit principal on every request.

| Principal kind | Derived from | May request | May approve |
| --- | --- | --- | --- |
| `assistant` | MCP transport (static connector id from config; **not** the MCP session id) | T0 reads; proposals for T1+ | never |
| `operator` | Panel login (passkey, or password + TOTP) | everything its tier allows | T1; T2/T3 with step-up proof |
| `local-root` | Unix socket `SO_PEERCRED` uid 0 | everything | T1; T2/T3 with TOTP |
| `system` | scheduler/runbook engine acting on an already-approved plan | only steps inside an approved plan | never |

- The MCP session id (`mcp_<hex>`, or `id(session)` fallback in `_session_key`) is kept only as `client_session`, an informational correlation field. It never appears in an authorization decision. This is already true of the broker's lease lookup; 0.4 makes it a stated invariant and removes it from audit columns that read like identity.
- **The approver must be a different principal kind from the requester.** The broker, not the bridge, verifies this (§3.4).
- Single operator for now (`owner`); the `operator_id` field leaves room for roadmap Q14.

### 3.3 Operations: proposal-on-first-call, parameter-bound approval

Replace scope leases as the primary mutation gate. **[R]**

1. A typed mutation tool (`restart_service`, `revoke_node`, …) called without an `operation_id` validates inputs, runs preflight, and **creates a proposal** `{operation_id, kind, target, params, params_sha256, tier, reversible, impact, preflight, expires_at}`. The tool result carries the approval card (same UI resource as today). One tool call, no `AUTHORIZATION_REQUIRED` hop.
2. The card renders **from the structured proposal** (kind, target, exact params, diff/impact, reversibility, tier). The model's `reason` is shown, labelled "Assistant's stated reason".
3. The human approves in the card or the panel. T2/T3 require a step-up proof (§3.4). Approval creates a grant bound to `(operation_id, params_sha256)`; one use; short expiry.
4. Execution is by either:
   - **Approve & run** (default): the approve call executes the operation server-side and the card shows live state; the model gets the result via `get_operation`. Removes the model round trip and works when `sendFollowUpMessage` is unavailable.
   - Retry of the same typed tool with `operation_id` (kept for hosts that need the model in the loop).
5. The broker executes only operations whose `(kind, params_sha256)` match an unconsumed grant it holds itself. A changed parameter needs a new proposal and approval.
6. **Timed leases stay, narrowly**, as an optional *operator window* for T1 routine ops (e.g. "allow service restarts for 15 min") created from the panel or a card. They are never offered for T2/T3.
7. Operation states: `PROPOSED → APPROVED → EXECUTING → SUCCEEDED | FAILED | UNKNOWN | EXPIRED | DENIED | CANCELLED`, plus `VERIFIED` when a post-check ran. `UNKNOWN` is explicit (ADR 0005): a timed-out or interrupted execution is reconciled against authoritative state, never assumed.

### 3.4 Broker v2

**[R]** Keep the broker a typed-operations executor. Changes:

- **Approver proof verified in the broker.** `grant` for tier ≥ T2 requires proof the broker can check itself and that is bound to the proposal: today's TOTP (already held by the broker, replay-protected) over `(operation_id, params_sha256)`; later optionally a WebAuthn assertion with the public key enrolled locally by root. A compromised bridge can relay but not forge. T1 may accept a host-attested click (documented as the weaker tier), and **the broker rejects grants arriving without a principal kind of `operator` or `local-root` claim plus whatever proof the tier needs**. The bridge's claim alone does not satisfy T2+. (A compromised bridge can lie about the principal for T1; that is why T1 is limited to low-impact, reversible ops and is the explicit trade-off of keeping a card-click approval path.)
- **Hello/capabilities handshake** (`hello` → broker version, protocol, supported operation kinds, `2fa.configured`, tier policy). Needed for ADR 0006 (bridge/broker skew during `deploy.sh`) and surfaced via `get_capabilities`.
- **Concurrency and long operations.** Handle connections concurrently (or at minimum separate the approval/read socket path from long-running work); long operations (`update.*`, `package.install`, runbook steps) become *start → poll* with an `operation_id`, per-op client timeouts, and no blocking of grants.
- **Operation ledger.** Persist `{operation_id, kind, params_sha256, state, started, finished, result_digest}` so the Admin service can answer "did it run?" after a timeout/restart (precondition for ADR 0005).
- **Privileged audit with parameters and tamper evidence.** Record `principal`, `approver` and method, `operation_id`, redacted params + digest (including node capabilities granted), and chain each record with a hash of the previous. Admin-side audit rows are marked non-authoritative.
- **Config apply by hash, not by content.** For managed config targets: Admin stages a candidate file in a staging dir; the broker verifies its SHA-256 equals the approved proposal's, runs the per-target validator, writes atomically, keeps a rollback copy. No diff logic or editor in the broker.
- **Network-facing hardening**: because the sandbox user can reach loopback (F1), either add `IPAddressDeny=any` / `IPAddressAllow=` for the sandbox unit (breaking the documented `curl 127.0.0.1:4020` use unless allowed per-port with `SocketBindDeny`/nftables), or authenticate the MCP endpoint (§3.5). Doing both is cheapest and does not rely on either alone.

### 3.5 MCP adapter and endpoint trust

- The MCP endpoint should authenticate callers independent of the tunnel: a connector bearer token held in `/etc/privanet-chat-admin/` (not readable by `privanet-shell`) checked by the Starlette app, and rejected for requests from the sandbox's uid where the transport allows it. This protects against local processes, not against the tunnel, which stays the external boundary.
- `visibility:["app"]` stays as UI metadata. In 0.4 the app-only helpers shrink from six to three (`approve_operation`, `deny_operation`, `get_operation_state`), and none is a trust root: each is a client of the Operator API whose result the broker re-validates.
- Add MCP annotations to every tool (`readOnlyHint`, `destructiveHint`, `idempotentHint`, `openWorldHint`) so the host can apply its own defaults.

### 3.6 Mixed-version capability discovery (ADR 0006 made concrete)

Three negotiation layers, each additive, each reporting `supported | degraded | unsupported | unknown` with a reason:

1. **Admin ↔ broker:** broker `hello` (above). On skew, Admin degrades to read-only and reports `BROKER_VERSION_SKEW` rather than sending unknown ops.
2. **Admin ↔ Core:**
   - Today: Admin can read per-node `protocolVersion`, `daemonVersion`, `capabilities`, `resources`, `lifecycle`/`status`, and optional `services` from the node view/heartbeat **[V]**.
   - Needed from Core (Core ADR): `GET /v1/admin/capabilities` (coordinator version, protocol, admin-API feature flags, management-operation registry and versions) and an additive heartbeat field advertising which management operations a node supports *and its owner has enabled*.
3. **Admin ↔ applications (Search/Proxy/Drive):** a small `compat.json` shipped with each Admin release (app, version range, required adapter version, known-bad ranges, schema/shape probes such as "Search `/status` has `frontier`"). Evaluate it against what `/health`/`/status`/updater report; never lexical version comparison.

Operations are offered per target: `get_node` returns `supportedOperations` (and `unsupported: [{op, reason}]`); a mutation against an unsupported target returns `UNSUPPORTED_BY_TARGET` and **does not fall back to SSH/shell** (ADR 0003 already says so). Replace `get_node_version_drift` with a compatibility evaluation grouped by `(protocolVersion, daemonVersion, capability set)`, protocol mismatch = incompatible, software difference with same protocol = informational (matching Core's own dashboard semantics).

Tool-list staleness: keep tool names stable, add parameters additively, emit `tools/list_changed` where the host honours it, and keep deprecated names as aliases for at least one minor release with a `deprecated` note in the description.

### 3.7 Typed remote-node administration through Core

Admin plans; Core carries and enforces; the node owner remains sovereign. **[R, requires Core work]**

- **Management-operation registry in Core**, parallel to `JOB_TYPES` and `SERVICES` (Core's pattern: closed, versioned, schema-validated, lockstep-tested). Candidate v1 kinds: `node.drain`, `node.resume`, `node.maintenance.enter/exit`, `node.slots.set`, `node.diagnostics.collect` (bounded, redacted), `node.restart.request`, `node.update.request`. No kind accepts a command, path, URL or script.
- **Delivery over the existing outbound relationship** (ADR 0003): admin API enqueues an operation `{id, kind, params, idempotency_key, expires_at}` → delivered in the heartbeat response → node validates, applies its **owner policy**, acks `ACCEPTED|REJECTED(reason)|COMPLETED|FAILED`. States are Core-authoritative and queryable by id, which is what makes ADR 0005 reconciliation implementable.
- **Owner control.** A node executes a management kind only if its owner enabled it locally (the same per-capability opt-in Core already requires for job types), and a kind can be granted or withheld at enrollment/approval time using the existing enrollment capability ceiling. This is how operator-owned nodes (full management) and community nodes (none, or drain-only) differ (roadmap Q15).
- **Authenticity.** Operations should be signed by the Coordinator (Core has a ticket-signing key and a verification-key route since 0.4.0-alpha.2, `PHASE4_DESIGN` §16; reusing it is plausible but must be confirmed in the Core ADR) and carry a nonce/expiry for replay protection.
- **Scoped Core admin credentials** (read / node-ops / enrollment / storage) so Admin's blast radius is proportional to the operation, and an `on-behalf-of` audit field so Core's log can name the Admin principal/approver.
- **Offline behaviour** (roadmap Q4): queued operations show `QUEUED` with expiry; an offline node is reported unreachable. Admin does not SSH, does not shell out, and does not simulate. For the *local* node, Admin can continue to use the local CLI through the broker as today.
- **Unification at the tool layer:** `set_node_slots(node)` resolves `node` to local (broker → `privanet-node slots`) or remote (Core op) and reports which transport and capability it used.

### 3.8 Update and self-update policy

Keep your rule: verified updates may use the automatic `privanet.updates` policy; arbitrary packages and root commands keep stronger authorization. **[R]** Define the boundary precisely.

**What "verified" must mean for the automatic policy** (all must hold; otherwise the update is a normal T2 proposal):
1. Authenticity independent of the download origin: release manifest *and* archive signed by a key pinned on the host (`/etc/privanet/release-keys/`), e.g. minisign/ed25519. SHA-256 from the same origin remains a corruption check, not authenticity.
2. Monotonic: strictly newer version by numeric ordering; never a downgrade or same-version reinstall unless `force` through an approval.
3. Same series: patch (and pre-release increments) within the installed major.minor, matching Core's updater policy; a new minor/major or a release flagged `requires_approval`/`migration` becomes a proposal with release notes in the card.
4. No unpinned dependency resolution as root: wheels vendored in the release or installed from a hash-locked requirements file.
5. Rate-bounded and single-flight (lock; at most N per hour).
6. Preflight (disk space, no conflicting runbook), snapshot before, post-update verification, rollback on failure.

**Policy knob** (Admin config, default shown): `updates.policy = auto-patch` | `approve-all` | `manual`; `updates.chat_admin = same as apps | approve`.

**Plan-bound apply.** `get_updates` returns a plan `{plan_id, per-app current→target, notes summary, compat result, would_be_policy: auto|needs_approval|blocked, reasons}`. `apply_updates(plan_id)` applies exactly that plan (hash-checked); if the world changed it returns `PLAN_STALE` with a new plan.

**Self-update as a runbook.** Steps: preflight → snapshot → install → restart broker/bridge → verify (`broker.version == bridge.version == target`, `hello` OK, a read probe) → mark complete; on failure → rollback to previous release symlink and mark `ROLLED_BACK`. The run record lives in Admin SQLite *and* the broker ledger, so a restart in the middle resumes at "verify" instead of being lost. The MCP client sees a stable `operation_id` it can poll after reconnecting.

**Interim, until signing exists (Stage 0):** treat `update_chat_admin` as T2 (approval required) and add the monotonic/series guard in `update.sh` and pinned dependencies to `deploy.sh`. This is a smaller change than signing and removes the zero-prompt root-code path. Because this narrows behaviour you shipped in 0.3.3, I am flagging it as a decision for you rather than assuming it.

### 3.9 Audit, history, runbooks

- **One event model** with correlation: `request → proposal → approval(grant, approver, method) → execution(step…) → verification → rollback?`, all keyed by `operation_id` / `run_id`.
- **Authoritative vs informational.** Privileged events live in the broker's hash-chained log (root-only). Admin DB holds non-privileged events and the read model; the timeline merges both and labels each source. Missing broker data is shown as a gap, not an empty list (F4).
- **Runbooks** (ADR 0005) as typed Python state machines first (answer to roadmap Q10: hard-coded, not YAML, not plugin-extensible — a declarative step list can be exposed read-only for display). Each step: preconditions, idempotence, timeout, retry, success criterion, post-verify, compensation if real, `NEEDS_OPERATOR` state. Privilege checkpoints inside a runbook are ordinary proposals/approvals; an approved **plan** can pre-approve a fixed list of T1 steps, never T2/T3 steps.
- **First vertical slice (ADR 0005's own):** drain → wait for jobs → verify → resume, plus set-slots, on a Core that has the management ops. Resume after Admin restart by querying Core's operation state by id.
- **History UX:** `get_audit_timeline(filter)` for the model; the panel renders the same data as a vertical timeline with per-operation drill-down, exportable.

## 4. Admin panel UI directions

All three reuse one set of components (approval card, node card, operation timeline, update plan) so the MCP App and the panel look and behave alike.

### Direction A — MCP-App-only (cards inside ChatGPT)

What: no standalone surface; richer widgets (overview, node list, timeline) rendered by the host.

| Pros | Cons |
| --- | --- |
| No new listener, no login/session/CSRF to build | Host controls size, lifetime and fullscreen; no persistence between messages |
| Zero new exposure | Cannot be a trustworthy approver channel (F1); TOTP still typed into the host iframe |
| Fastest to ship | No push/notifications, no state when the chat is closed, weak on mobile for history |
| | Every refresh costs a model/tool round trip |

### Direction B — Standalone local web panel (PWA) over the Operator API

What: Admin serves a small SPA/PWA from `127.0.0.1:8788`; reachable remotely only by whatever tunnel/VPN the operator chooses; login by passkey or password+TOTP; sections: Overview, Nodes, Approvals inbox, Updates, Runs, Audit timeline, Settings/policy.

| Pros | Cons |
| --- | --- |
| Persistent; works without ChatGPT; real approvals inbox and history | New attack surface; needs auth, CSRF, CSP, rate limiting (Core's `local-ui` guard is a ready template to port) |
| A proper approver channel with step-up bound to the proposal | Remote reachability is an operator problem (roadmap forbids requiring VPN/WireGuard for normal node admin; the *panel* is a different matter but still needs an access story) |
| Best mobile story (PWA, passkey instead of typed TOTP) | More code and a front-end build/test discipline |
| Natural home for runbook progress, update plans, policy editing | Duplicates part of Core's `privanet-admin ui` unless the boundary is explicit |

### Direction C — Hybrid (recommended)

What: Operator API first; MCP cards for contextual moments (approval, node, run progress); panel for persistence, inbox, history, and as the **strong approver channel**. Every card has "Open in panel"; the panel shows pending approvals created from chat; approving in either place resolves the same operation.

| Pros | Cons |
| --- | --- |
| Chat stays the primary interface (roadmap §8) while approvals gain a real authenticated channel | Two renderers to keep consistent (mitigated by shared components) |
| Staged: read-only panel first (low risk), approvals later | Most total work of the three |
| Graceful when the host refuses fullscreen or widgets | |

### Rejected: extend Core's `privanet-admin ui`

It is Core's operator dashboard for Core entities, driven by the single all-powerful admin secret with no operator identity. Folding Admin's approvals/policy/update orchestration into it would violate ADR 0001 (Core must stay usable and minimal without Admin) and couple release trains. The Admin panel should link to it (or embed read-only node data via the Operator API) rather than extend it, and the Core ADR on scoped admin credentials should give it a read-only token.

**Recommendation: C, built B-read-only first** (Stage 3).

## 5. Recommended 0.4 tool taxonomy

Conventions **[R]**: observe tools are `get_*`/`list_*`, side-effect-free, `readOnlyHint=true`; mutating tools are imperative verb + noun, typed, carry `destructiveHint`/`idempotentHint`, and follow proposal-on-first-call; one noun per resource (`node`, not `node_reference`); one `operation_id` instead of `authorization_request_id` + `confirmation_request_id`; every result uses one envelope:

```json
{ "ok": true, "code": "OK", "data": {}, "warnings": [],
  "freshness": {"source": "core|systemd|search|cache", "asOf": 0},
  "sections": {"nodes": "ok", "search": "unavailable"},
  "operation": {"id": "op_…", "state": "PROPOSED", "tier": 2, "approval": "pending"},
  "unsupported": null }
```

### 5.1 Observe (read-only, no approval)

| Tool | Replaces / notes |
| --- | --- |
| `get_capabilities` | New. Admin/broker/Core/app versions, API versions, per-target supported operations, approval policy, 2FA configured (folds `get_sudo_2fa_status`), runbook catalog |
| `get_overview(sections?)` | `get_privanet_summary`; per-section status + freshness; never fails wholesale; no network side effect (update state from cache) |
| `list_nodes(status?, include_revoked?)`, `get_node(node)` | `get_nodes`, `get_node`, `get_node_version_drift`, `get_local_node_slots`; node view includes compat verdict and `supportedOperations` |
| `list_join_requests(include_all?)` | `get_pending_nodes` |
| `list_services`, `get_service(service)`, `get_service_logs(service, lines, priority?)` | `get_services`, `get_service_status`, `get_recent_logs` |
| `get_host_health` | `get_system_health` |

| `diagnose(subject_kind, subject)` | `diagnose_node` and roadmap `diagnose_*`; findings `{severity, evidence[], impact, safe_action: proposal-template, required_tier}`; fixtures taken from Core's schema |

| Tool | Notes |
| --- | --- |
| `run_command` | Unchanged semantics. Recorded as an `operation` (kind `shell.run`, T0) so it appears in the one timeline. Output redaction as today. |

### 5.3 Mutate (proposal-on-first-call)

| Tool | Tier | Notes |
| --- | --- | --- |
| `restart_service(service)` | T1 | allowlist unchanged; eligible for operator window |
| `decide_join_request(code, decision, capabilities?, label?)` | T2 | approve/deny; card lists the exact capabilities; capabilities are part of `params_sha256` (fixes F2) |
| `rename_node(node, name?\|clear)` | T1 | |
| `revoke_node(node)` | T2 (step-up) | single card, target-bound; replaces two-card flow |
| `set_node_slots(node, slots?\|clear)` | T1 | local via broker today; remote via Core op when discovered |
| `set_node_state(node, state: active\|draining\|maintenance)` | T1/T2 | remote, discovery-gated; reversible |
| `collect_node_diagnostics(node)` | T1 | bounded, redacted, async |

| `start_runbook(kind, params)`, `control_runbook(run_id, action: resume\|cancel)` | per steps | plan approval can pre-approve T1 steps only |
| `install_system_package(package)` | T3-lite | one card with scope+exact package, TOTP step-up; root `apt-get` is root-equivalent |
| `run_root_command(command, reason)` | T3 | replaces `request_sudo_command` + `run_sudo_command`; exact command stored before approval, TOTP, one use; second call takes only `operation_id` |
| `revoke_approval(operation_id?\|all)` | T0 (always allowed) | replaces `revoke_admin_access` |
| *Later (Stage 5):* `create_backup`, `list_backups`, `restore_backup` | T1/T1/T2-step-up | |

Model-visible count: observe 18 + act 1 + mutate 16 = **35**, plus 3 backup tools later (`create_backup`, `list_backups`, `restore_backup`) = **38**. That is the same order as today's 38, but it now covers remote operations, config, runbooks, rollback and approvals, and about half of the surface is typed verbs with stable schemas and annotations. I am not claiming a smaller surface; the gain is that no tool exists only to operate the approval mechanism (3 `request_*` tools and 2 status tools go away), and app-only helpers drop from 6 to 3. If the count proves too high for a host, the first merge candidates are `list_nodes`+`get_node`, `list_services`+`get_service`, and `list_operations`+`get_operation` (each with a list/detail switch) rather than a generic `execute(kind, params)`, which would lose per-verb schemas and annotations.

### 5.4 App-only (UI helpers; not trust roots)

`approve_operation(operation_id, duration?, step_up?)`, `deny_operation(operation_id)`, `get_operation_state(operation_id)`. Down from six. Each is a client of the Operator API and is re-validated by the broker.

### 5.5 Removed from the model surface

`request_admin_access`, `request_action_confirmation`, `request_sudo_command`, `get_authorization_status`, `get_sudo_2fa_status`, `get_nodes`/`get_pending_nodes`/etc. (renamed). Old names remain as deprecated aliases for one minor release (§3.6).

### 5.6 Tier definitions

| Tier | Meaning | Approval | Examples |
| --- | --- | --- | --- |
| T0 | Observe / unprivileged | none | all `get_*`, `run_command` |
| T1 | Routine, reversible | card click (host-attested allowed); optional operator window | restart service, rename node, set slots, drain |
| T2 | Impactful / hard to reverse | exact-params proposal, one use, step-up proof verified by broker (TOTP initially; configurable per kind), never timed | approve join with capabilities, revoke node, config apply, minor update, restore |
| T3 | Root-equivalent | exact command or package, TOTP, one use, 120 s window | `run_root_command`, `install_system_package` |
| Automatic | verified patch updates only | none, within §3.8 bounds | `apply_updates` for a plan that meets all six conditions |

Scope names (`privanet.*`, `system.*`) stay as the technical vocabulary for the broker and policy; tiers are the UX concept.

## 7. Staged implementation plan

Stages are ordered by dependency and risk. Exit criteria are testable. "Core" items run in parallel in the Core repo and are the critical path for remote administration.

### Stage 0 — 0.3.x hardening of verified defects (no new product surface)

Fits the roadmap's 0.3.4–0.3.6 and should land before 0.4 work is built on top.

1. **Close F1.** (a) authenticate the MCP endpoint with a connector bearer token unreadable by `privanet-shell`; (b) restrict sandbox loopback (IPAddress filtering, explicit allow for the documented health-check port or an allowlist); (c) require TOTP (or local-root) for grants of `privanet.nodes` and `system.packages` until proposal-bound approvals ship; (d) add the Appendix A scenario as a CI test (real broker + server on temp paths, HTTP client as "sandbox"; must fail to obtain a lease without the connector token and without proof).
2. **Correct the README/ADR claim** that `run_command` cannot mint approvals; add the test that keeps it true.
3. **Fix F3.** Per-action client timeouts; make `update.*` and `package.install` start/poll or at least non-blocking for grants; thread the accept loop; make `privanet_summary` return per-section status.
4. **Fix F6.** Read `resources.pressure`, handle `STALE`/`DRAINING`/`OFFLINE_EXPECTED`, compare protocol rather than version string; replace invented fixtures with fixtures generated from Core's schema (contract test pinned to a Core release).
5. **Fix F5 interim.** Monotonic + same-series guard and lock in `update.sh`; hash-locked or vendored dependencies; make `update_chat_admin` require approval until signing lands.
6. **Fix F4.** Broker audit records params (capabilities) and surfaces broker-audit failures in `get_audit_log`.
7. **Add `get_approval_status`-equivalent** (pending/denied/expired/consumed) and fix `authorize.py` scope list.
8. **Hygiene.** `.gitignore`, delete tracked `.pyc`, single `VERSION` source, CI on all branches/PRs, shellcheck, lint, tools-list contract test (names, visibility, annotations), replace source-grep tests with behavioural ones where a boundary is asserted, update `ROADMAP.md` baseline (0.3.3.1).

Exit: new CI test proves an unprivileged local process cannot obtain a scoped grant; full pytest + contract tests green; real-host smoke test of update through the bridge with the 10 s client timeout.

### Stage 1 — Service layer, principals, operations (Admin only, no new transports yet)

1. Extract the service layer from `core.py`; MCP handlers become thin.
2. Admin SQLite schema (ADR 0004): `schema_version`, `operations`, `approvals`, `audit_events` (non-privileged), `policy`.
3. Principal model and `client_session` rename; MCP connector principal from config.
4. Proposal-on-first-call for existing mutations; `operation_id` replaces the two request IDs; new `get_operation`, `list_operations`, `get_capabilities`; envelope and annotations on all tools; old names as aliases.
5. Card renders from the proposal; states `PROPOSED…SUCCEEDED/UNKNOWN`.

Exit: every existing mutation works end-to-end through one card; old names still work; contract test pins names and annotations.

### Stage 2 — Broker v2

1. `hello`, versioned envelope, operation ledger, hash-chained privileged audit with params.
2. Grants bound to `(operation_id, params_sha256)`; step-up proof (TOTP) verified in the broker for T2/T3; T1 policy limited to low-impact ops.
3. Concurrent connections; long operations as start/poll.
4. Fold sudo into `run_root_command`, package install into T3-lite; remove separate confirmation flow.
5. Config-apply-by-hash plumbing (no targets yet).

Exit: a compromised-bridge test (bridge forges principal/approval) cannot execute T2/T3; kill/restart tests show `UNKNOWN` reconciliation via the ledger; skew test (old bridge ↔ new broker and reverse) degrades safely.

### Stage 3 — Operator API and panel (read-only first)

1. Operator API over unix socket + loopback HTTP; same service layer.
2. Panel v0: login, Overview, Nodes, Audit timeline, Updates (plan view). Port Core's local-ui guard (token→HttpOnly SameSite=Strict cookie, Host allowlist, Origin+CSRF on writes, nonce CSP, strict body limits).
3. Then approvals inbox with step-up (TOTP first, passkey optional later) and "Approve & run"; "Open in panel" from cards.
4. Shared card components; mobile layout pass; a headless-browser smoke test in CI.

Exit: an operation proposed in chat is approvable only via a verified approver path from either surface; the panel works with ChatGPT unreachable.

### Stage 4 — Core protocol (parallel; blocks remote tools)

1. Core ADR (§6.3) accepted.
2. Core: scoped admin credentials; `GET /v1/admin/capabilities`; management-operation registry; first vertical slice **drain / resume** and **set slots**; heartbeat advertisement; operation state API; signed envelope; protocol and mixed-version tests per Core's own `compat-previous-release` pattern.
3. Admin: Core adapter using the read-only credential (stop routing reads through the root broker); `set_node_state`, `set_node_slots(node)`, `collect_node_diagnostics` gated by discovery; compatibility evaluation replaces version drift.

Exit: drain/resume of a remote node works against a real Core alpha, is resumed correctly after an Admin restart (ADR 0005 slice), and an older Core/node yields `UNSUPPORTED_BY_TARGET`.

### Stage 5 — Orchestration

1. Runbook engine (typed state machines) with durable checkpoints.
2. Update policy engine, signed releases, plan-bound `apply_updates`, rollback, release-note summary; self-update as runbook.
3. `drain_and_update_node`, `update_priva_stack` (dependency order, canary, post-verify, rollback) using Core's `privanet-update` for Core apps.
4. Structured config management for Chat Admin itself first, then Core/node policy, Search, Proxy.
5. Backups (`create/list/restore`), restore as T2 step-up.

Exit: staged update of a two-node deployment with an injected failure rolls back and leaves a coherent timeline.

### Stage 6 — Hardening and release gate (roadmap Phase 5)

Misbehaving/malicious node tests, broker fuzzing including the new envelope, mixed-version matrix, interrupted updates, unreachable nodes, corrupted Admin DB (Core keeps operating, ADR 0004), rollback failures, restore verification, and three consecutive full audit passes with no new actionable findings before calling 0.4 stable.
